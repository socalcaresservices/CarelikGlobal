## 1. What this adds (and what it leaves alone)

| | Pilot / test slice (unchanged) | Production (new) |
|---|---|---|
| CDK context | `-c env=prod` | `-c env=prd` (alias `production`) |
| Stacks | `Ogevia-prod-*` | `Ogevia-prd-DatabaseSecret`, `-EvidenceStorage`, `-WebHosting`, `-ServiceVerificationApi`, `-Observability` |
| Database | `ogevia_sv_test` | `ogevia_prd` (same RDS instance, separate database) |
| App login / secret | existing `ogevia/database/app` | `ogevia_prd_app` / `ogevia/prd/database/app` (generated by Secrets Manager, retained) |
| Lambda `DB_NAME` | `config.database.name` = `ogevia_sv_test` | `config.database.name` = `ogevia_prd` |
| Evidence bucket / KMS | existing | new `ogevia-prd-signature-evidence-...` |

Single source of the Lambda's database: `infra/aws/lib/config.ts` (`database.name`). Nothing is set by hand on the Lambda.
Fail-closed: `assertDatabaseConfig` (synth), the API stack (no secret = no stack), and `loadConfig` at Lambda cold start (`OGEVIA_ENV=prd` requires `DB_NAME=ogevia_prd`; the secret's `dbname` must match). Production never falls back to `testSlice`.

One additive change touches the pilot: `Ogevia-prod-NetworkEgress` endpoint policies also admit the production secret, evidence bucket and identity function (private-DNS interface endpoints are unique per VPC, so production shares them). Verified by template diff: that is the only template change for `env=prod`, apart from the API Lambda code hash (the runtime check above; behaviour unchanged for `OGEVIA_ENV=prod`).

## 3. Run it (operator shell with admin AWS credentials, session-manager-plugin, psql)

```bash
cd infra/aws
AWS_PROFILE=<admin> ./scripts/deploy-production.sh check     # read-only; run first

OGEVIA_DEPLOY_APPROVAL=<approval-ref> \
OGEVIA_ADMIN_EMAIL=admin.ogevia@gmail.com \
OGEVIA_ADMIN_NAME="<display name, optional>" \
AWS_PROFILE=<admin> ./scripts/deploy-production.sh all       # interactive terminal (CDK confirms IAM changes)

OGEVIA_DEPLOY_APPROVAL=<approval-ref> AWS_PROFILE=<admin> ./scripts/deploy-production.sh web
```

Order inside `all`: check -> snapshot -> secret -> egress -> database -> infra -> smoke. The API stack is created only after the database is migrated, the login, tenant and administrator exist, and the access checks pass.
Each step is re-runnable. On failure the script prints the failed step (never a secret) and exits non-zero.

Administrator: Cognito invitation (`AdminCreateUser`, emailed temporary password, password change + TOTP MFA at first sign-in; pool MFA must be `ON` or the script stops). If the identity already exists it is reused (no password reset, no duplicate) and linked as `organization_owner` of SoCal Care Services. The manager, caregivers and any other pilot account get **no** production membership; add them in the application. The manager's financial restrictions come from the role grants in the migrations and are unchanged.
There is no administrator invitation route in the application (the invitation flow in 0025 invites caregivers only), so the first owner is created with Cognito's own invitation plus `13_prd_bootstrap_admin.sql`.

## 4. Smoke tests (script `smoke`)

1. Lambda environment: `DB_NAME=ogevia_prd`, `OGEVIA_ENV=prd`, production secret ARN, not the test secret, no secret-looking variables.
2. Anonymous API call returns 401.
3. A well-formed unknown public token makes the Lambda open its connection; `pg_stat_activity` must show `application_name=ogevia-sv-api` on `ogevia_prd` as `ogevia_prd_app`, and none on the test database.
4. In `database`: the production login connects to `ogevia_prd` only; the test-slice credential is refused on `ogevia_prd` (PUBLIC has no CONNECT; only `ogevia_prd_app` is granted).

Not scripted (needs a signed-in browser, do once after `web`): sign in as the administrator with MFA; create a clearly labelled synthetic client; confirm a caregiver-role user cannot see agency data; capture a signature and confirm the object lands in the `ogevia-prd-signature-evidence-...` bucket. Delete or void the synthetic record afterwards through the application's supported path; do not let it reach billing.

## 5. URL

The production frontend origin is the `WebOrigin` output of `Ogevia-prd-WebHosting` (a CloudFront domain, built with `VITE_APP_ENV=production` and the production API URL). `app.ogevia.com` is not repointed by this work: that is a DNS change that needs a separate owner decision. `https://d2xumch5w0izfg.cloudfront.net/` is the pilot (test database); do not use it as the production URL.

## 6. Rollback and recovery

- Rollback anchor: RDS manual snapshot `ogevia-prod-postgres-pre-prd-<UTC date>` (taken by `snapshot`; restore only to a NEW instance).
- The pilot database, stacks and users are not modified, apart from the additive egress policy entries. To revert them: check out the previous commit and `cdk deploy Ogevia-prod-NetworkEgress -c env=prod -c mode=deploy --exclusively`.
- Failure before `infra`: nothing serves traffic. Fix the cause and re-run the failed step. `ogevia_prd` and the secret are retained; re-running is idempotent.
- Failure in `infra`: CloudFormation rolls the failed stack back; the database is untouched. Re-run `infra`.
- Failed migration: that file's transaction rolls back; the ledger shows the last applied version. Fix forward with a new numbered migration (applied files are checksummed; never edit one).
- Back out production completely: `Ogevia-prd-*` stacks have termination protection and the database, secret and buckets are retained. Deleting any of them is a RED action in CLAUDE.md and needs a separate explicit instruction.
