## 1. Scope

The first production milestone is **Service Verification (SV)** only (`CLAUDE.md` §2). Everything else (candidates/hiring, documents, incidents, Stripe billing, platform admin) stays on Supabase and Netlify until later phases. Nothing is retired until AWS parity passes the acceptance gates.

### 2.3 Business invariants to preserve (VERIFIED in SQL)

1. **Server timestamps.** `time_in` and `time_out` come only from `now()` inside `start_ad_hoc_service_visit` and `end_service_visit`. No timestamp parameter exists.
2. **One open visit per caregiver.** Enforced by partial unique indexes `service_visits_one_open_per_caregiver_user` and `…_record` over `status in ('draft','awaiting_signature')`, plus `pg_advisory_xact_lock` per caregiver on start.
3. **One active visit per scheduled shift.** Enforced by the `service_visits_shift_unique` partial index.
4. **Assignment gate.** `caregiver_has_active_assignment()` uses the organization's local date (`organizations.timezone`, default `America/Los_Angeles`).
5. **Authorization resolved server-side** with `FOR UPDATE`. The cap is computed in minutes, and `worked_minutes`, `verified_minutes`, and `billable_minutes` stay separate. The cap never erases worked time.
6. **End is retry-safe.** A repeat `end_service_visit` returns the original timestamps.
7. **Confirmation methods.** `draw` and `assisted_mark` need a signature object at the exact path `{org}/{visit}/client-signature.png`. `typed` and `verbal` need a signer name. `unable_to_confirm` needs a reason. Only draw and mark count as confirmed. Every other method gives `billable_minutes = 0` and routes the visit to `administrator_review`.
8. **Lock on confirm.** `signed_at` and `locked_at` are set. No UPDATE RLS policy exists, so all writes go through SECURITY DEFINER RPCs.
9. **Append-only correction.** The original row becomes `status='corrected'`. A new row is linked via `original_visit_id`. A `visit_corrections` row stores actor, reason, and before/after snapshots. Overlapping or future corrections are rejected.
10. **Billing Ready ≠ billed.** `list_billing_ready_visits` covers `status='signed'` with no active approval. `approve_visit_for_billing` is an authenticated human action, and `submit_billing_approvals` is separate.
11. **Financial separation.** Managers can't see or set rates (`protect_authorization_financial_fields`, `redact_financial_audit_values`).
12. **Signature object path** holds only UUIDs, never client identity.

## 4. Target request path (unchanged from `CLAUDE.md` §4)

```
React (Netlify) → Cognito (ID/access token) → API Gateway (JWT authorizer)
  → Lambda (Node 22, TypeScript) → RDS PostgreSQL (private, via RDS Proxy only if justified)
                                  → S3 (presigned PUT/GET, short TTL)
```

- **Porting the RPCs.** Keep the PostgreSQL functions as the business-logic layer, which is the least rewrite (`CLAUDE.md` §5). Replace `auth.uid()` with a transaction-local setting that Lambda sets from the verified Cognito `sub`: `set local app.user_id = $1` after mapping `sub` → `users.id`. Replace `has_permission()` membership lookups the same way. Lambda never accepts `organization_id`, role, timestamps, or amounts as trusted input.
- **RLS.** Keep RLS enabled on the ported tables as defense in depth. Lambda connects as a non-owner role without `BYPASSRLS`.
- **Signature flow.** The replacement for `storage.objects` existence checks works like this:
  1. `POST /visits/{id}/signature-upload`: Lambda verifies the caller owns the visit and it is `awaiting_signature`, then returns a presigned PUT for `{org}/{visit}/client-signature.png` with `Content-Type: image/png`, a size limit, and a 5-minute TTL.
  2. `POST /visits/{id}/confirm`: Lambda runs `HeadObject` to check existence, size, and content type, then calls the ported `confirm_service_visit` with the key. The DB stores the key, version ID, and SHA-256. It never stores image bytes.
- **Idempotency.** Start and confirm accept a client-generated `Idempotency-Key`. End is already idempotent.

## 6. Rollback strategy

- Until Phase 8, rollback means `VITE_SV_BACKEND=supabase`. Supabase keeps running and is not modified by the migration.
- Stateful AWS resources use `RemovalPolicy.RETAIN`, and prod stacks have termination protection.
- RDS: automated backups plus a manual snapshot before each migration. Migrations are forward-only and idempotent, and each has a documented reverse script where a reverse is safe.
