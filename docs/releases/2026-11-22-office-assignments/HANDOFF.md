## What the old "Dashboard Chart Color" controlled (item 3)
There was no per-caregiver colour field. The nearest setting is the chart **palette** (Care blue, Blue shades, Primary colors, Ogevia) chosen under Settings > Appearance / the Dashboard's "Chart appearance" link. It is stored per person (with an agency default) and colours chart series **by position**; it never identified a caregiver. The Reports chart used it for every grouping. It is unchanged.
- Exact path to the caregiver chart: **Operations > Reports > (Report list) Visits overview > chart "Group by" = Caregiver**.
- Roles that can open it: Administrator (organization_owner), Manager and Scheduler (all hold `visits.read`). Roles that also see the saved caregiver colours there: the same three (they hold a permission that reads the colour list). Caregivers and Coordinators cannot open Reports.
- New behaviour: when grouped by Caregiver, each slice/bar uses that caregiver's saved **Caregiver Color**; a caregiver with no colour keeps the palette colour. Other groupings are unchanged. The shared setting is labelled **Caregiver Color** (profile, list and picker).

## How to use the switches
Routes behind a switch do not exist while it is off; the web hides every office/colour control when its data does not load, so "off" is safe. The switches are keys in `features` of the environment in `infra/aws/lib/config.ts`: `officeAssignments` (8 routes: offices update/reactivate, assignments, counties, colour, facets) and `assignmentHistory` (1 route: who/when). Turn ON: set the key `true` for that environment and deploy the API stack (a routes-only change set, as in the Offices release). Turn OFF: set it `false` and redeploy; the routes disappear, data and the database stay. TEST does this through the release scripts (`TEST_H7...`, `TEST_H8...`), which patch the line for synthesis only and restore the file. Production: both switches are OFF in `config.ts` today and stay OFF until the production release (Approval A).

## Wrong-email invitation: end-to-end TEST (item 5), no passwords in chat or logs
Use an inbox you control; with plus-addressing use `you+wrong1@` as the WRONG address and `you+right1@` as the corrected one (otherwise two inboxes). Passwords stay in the emails; never paste them.
1. TEST site > Staff > Caregivers > Add caregiver "Wrong Email Test"; open it, App sign-in, invite to the WRONG address. Email 1 arrives (temporary password P1). Do not use it yet.
2. Lookup (read-only): `PROCEDURE=lookup SEARCH="Wrong Email Test"` shows `CG_CODE=...`, the masked address and "still pending (correctable): YES".
3. Check (read-only): `PROCEDURE=check CAREGIVER_CODE=<code> NEW_EMAIL=<right address>` -> PASS.
4. Correct: default procedure with the same code, your corrected address and a reason; type `CORRECT-INVITATION-EMAIL`. Email 2 arrives at the RIGHT inbox (P2). The output reports the account email, invitation email and contact email changed together, the SAME account, and one audit event.
5. P1 must be rejected: try signing in with the wrong address + P1, and the right address + P1: both fail.
6. Wait one minute (the app limits resends to one per minute and five per day), then Staff > Caregivers > Resend sign-in link: Email 3 arrives at the RIGHT inbox (P3); P2 stops working.
7. Sign in with the right address + P3: Ogevia asks for a permanent password.
8. Audit: Operations > Reports > Audit report (Administrator) lists `caregiver_invitation.email_corrected` with who and when.
Partial failure: if the database step fails the sign-in account change is reversed automatically and the output says so; if only the resend fails the account and Ogevia are already corrected and Resend finishes it. `PROCEDURE=check` and `lookup` show the current state at any time.
