# Ogevia Hostile Investor, Product, QA & Business Audit

**Date:** 2026-08-11
**Scope:** `socalcaresservices/carelikglobal` repository as of this commit — code, schema, migrations, docs. No production system was touched; no destructive action was taken. This is read-only research. A follow-up verification pass (see **Verification Addendum** at the end) later ran the actual test/build/lint suite locally and confirmed a subset of findings directly against the live `CarelikGlobal` Supabase project and the running app — read-only queries and unauthenticated page loads only, with explicit user sign-off before touching anything live.
**Method:** Nine-phase audit against the current codebase. Every claim is labeled **VERIFIED** (exact implementation found), **LIKELY** (partial/indirect evidence), **ASSUMPTION** (no code evidence either way), or **CONTRADICTED** (code does something different than the stated plan). Where information doesn't exist in the repo, that is stated as **UNKNOWN** rather than skipped. Governing instruction: keep auditing when information is missing, never stop at the first gap, and treat the current master-plan narrative as a hypothesis to attack, not a conclusion to defend.

---

## Headline finding, before the phases

The codebase's own foundational document, `docs/PRODUCT_CONSTITUTION.md`, states a *different* product identity than the one this audit was commissioned to test:

> "CareLik is a Workforce Operations Intelligence platform. It is not a scheduling app, not an EVV (electronic visit verification) system, and not a generic HR platform." (`docs/PRODUCT_CONSTITUTION.md:14-16`)

The master-plan framing this audit was built from — "reconciliation/billing-readiness layer" — is narrower than what's actually built and positioned in-repo. The shipped product (per `marketing-page.tsx` and the schema) is a full workforce-ops suite: caregiver/client matching (CareScore), scheduling, its own visit verification with signature capture, credentials/compliance tracking, incidents, an applicant pipeline, and — not mentioned in the master-plan summary at all — a real, live **Stripe subscription billing system** for Ogevia's own SaaS revenue (distinct from the agency's payer billing, which the platform deliberately does not touch). **This mismatch between stated identity and stated pitch is itself the first thing that needs resolving before any of the nine phases below can be acted on** — see Phase 9.

## Phase 1 — Verify what actually exists

- **VERIFIED.** Monorepo: pnpm workspaces + Turborepo, `apps/web` (React 18 + Vite 6 + React Router 7 + TanStack Query), `apps/netlify-functions` (2 functions: Stripe checkout + webhook), `packages/{auth,shared,ui}`, `supabase/` (80 migrations, 4 Deno edge functions). 56 page files (28 pages × test pairs), 43 test files total.
- **VERIFIED — branding is mid-transition, not complete.** A migration (`supabase/migrations/20260810000000_carelik_to_ogevia_rename.sql`) renamed the platform's own organization row from "CareLik" to "Ogevia" one day before this audit's date, explicitly because "nothing is live/in use on this platform yet." But the rename is partial: 68 files still reference "carelik" (package names `@carelik/ui`, `@carelik/shared`, `@carelik/auth`, doc titles, the `docs/PRODUCT_CONSTITUTION.md` header itself, `docs/BUILD_022...md`'s domain names `carelik.com`/`{slug}.carelik.com`) against 35 files referencing "Ogevia" (mostly the newer marketing/pricing pages and the rename migration). Anyone auditing "is this Ogevia" from the code alone will find a codebase that is still majority CareLik-branded internally.
- **VERIFIED — the platform is pre-launch.** Per the rename migration's own comment: "1 client, 0 authorizations, 0 completed visits across all three organizations" as of 2026-08-10. Nothing in this audit reflects live customer behavior — everything below is a capability audit, not a usage audit.
- **VERIFIED — real, not scaffolded, subscription billing exists.** `plan_definitions` (versioned plan catalog: Trial/Start $29/Grow $59/Pro $99/Scale $179 per month), Stripe Checkout (`apps/netlify-functions/functions/create-checkout-session.ts`), a webhook handler, and server-side usage-limit enforcement via Postgres triggers (`supabase/migrations/20260809162000_billing_usage_enforcement.sql`) are all live in the schema, built one day before this audit's date. This is a materially bigger claim than "billing-readiness layer" — Ogevia already bills its own customers for real money via Stripe; it just doesn't bill *payers* on the agency's behalf, which is the distinction Phase 2 makes precise.

## Phase 2 — Product value & workflow audit

Six specific master-plan claims were tested directly against code (full agent report on file; citations below are drawn from it).

| Claim | Verdict | Evidence |
|---|---|---|
| EVV/GPS stays external at launch | **VERIFIED** | Zero hits for `sandata\|EVV\|geofence\|lat\|lng` across all `.sql/.ts/.tsx`. Stated as policy in `PRODUCT_CONSTITUTION.md:14-16`. Visit timestamps come from server `now()`, explicitly to prevent client-clock spoofing — not location capture. |
| "Authorization → billing chain" | **LIKELY, overstated** | A real chain exists: `client_authorizations` → `shifts` → `service_visits` (capped against authorized hours, `20260809042943_service_verification.sql:571-686`) → signature → a printable report (`service-verification-reports-page.tsx`). It stops at a report. There is no `invoices` or `claims` table anywhere in 80 migrations. The repo's only tables matching `billing\|invoice\|claim` are Ogevia's *own* Stripe subscription billing — unrelated to agency payer billing, and easy to conflate on a shallow grep. **"Billing-readiness layer" is accurate; "billing chain" is not — nothing generates a bill.** |
| "Four-screen workflow" (intake → verification → reconciliation → billing) | **CONTRADICTED** | No screen or route corresponds to "reconciliation" or "billing/claim" anywhere in `apps/web/src/pages`. What exists are two unrelated 4-step *wizards* — a scheduling wizard (`staff-visits-page.tsx`: Client → Service → Date/time → Review) and a verification flow (`service-verification-page.tsx`: Start → In progress → Caregiver review → Sign). Neither includes reconciliation or billing. The four-screen claim as described does not match any actual screen sequence. |
| Internal UUID + separate "random client code" for privacy | **VERIFIED** | `clients.id` is a UUID; `client_code` (`CL-XXXXXX`) is a separate, non-identifying field. Caregiver-facing RPCs return only the code, never the legal name (`list_service_verification_options`, comment: "Names stay out of the caregiver workflow entirely," `20260809042943_service_verification.sql:265-267`). **Gap:** the admin `clients-page.tsx` never displays `client_code` at all — the privacy-by-design mechanism exists in the data layer but isn't surfaced in the primary admin UI. |
| Billing approval is human-in-the-loop | **VERIFIED, narrower than implied** | `approve_visit_billing()` requires a human with `visits.manage` and only fires when a visit exceeds its authorization cap (`resulting_visit_status := 'administrator_review'`). Visits *within* the authorized cap auto-transition to `signed` with **no human step**. Human approval is an exception-path control, not a review of every billable visit. |
| Authorization changes are versioned | **LIKELY, not a real version model** | `authorizations-page.tsx` does a plain in-place `update()` — no `version` column, no history table (contrast with `visit_corrections`, which *is* a purpose-built before/after table). What exists is the generic audit-log trigger, which captures a diff but isn't a queryable version history the way "versioned" implies. |

### The central open question this audit was asked to force: is Ogevia adding work, not removing it?

Marketing copy states caregivers "clock in and out from their phone, capture a client or representative signature on the spot, and every visit is locked and auditable the moment it's signed" (`marketing-page.tsx:24-28`). Code confirms this is real and fully separate from any state-mandated EVV system (California's CalEVV/Sandata or equivalent) — there is no integration point, no data exchange, no mapping between Ogevia's `service_visits` and any external EVV record, anywhere in the codebase.

That means the "external EVV" decision is **technically true** (no GPS/Sandata code exists) but it does **not** resolve the substantive risk: a caregiver in a state with mandatory EVV would plausibly clock in/out through the state's EVV app or device *and* go through Ogevia's separate clock-in/verify/sign flow for the same visit. Nothing in the code shows this has been designed away — there's no "already verified via EVV, skip re-verification" path, no import/reconciliation of external EVV records, no evidence this was even considered as a workflow. **This should be treated as CONFIRMED-AS-UNRESOLVED, not dismissed**: the code doesn't contradict the "keep EVV external" pitch, but it also provides zero evidence that double-work has been designed out. This is the single highest-leverage open question in the whole audit, because it determines whether "we deliberately don't integrate EVV" is a moat (avoided integration cost, avoided vendor risk) or a liability (customers do two workflows per visit instead of one).

### Other value gaps found
- **CareScore's "proximity" is not real distance.** `docs/design-system.md:270-274,286-287`: "CareScore's proximity component is a zip/city/state text match, not real distance." Marketing copy lists "proximity" as a factor in "a real, computed match score... not a guess" (`marketing-page.tsx:20-22`) — this is defensible as *directionally* true but overstates precision to a prospect who assumes geolocation.
- **GeoScore does not exist.** The `ScoreBadge` component that would show it is explicitly gated behind a `preview: true` prop and sample data (`design-system.md:269-281`) — a disciplined way to avoid faking a number, but confirms the feature named in early product materials isn't built.

## Phase 4 — Hostile QA, failure modes & edge cases

- **VERIFIED — test coverage is broad, not superficial.** 28/28 page files have matching test files; strict TypeScript (`tsconfig.base.json`: `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`) is meaningfully above-average rigor for a project this size.
- **VERIFIED — CI has a real gap.** `.github/workflows/ci.yml` runs `typecheck`, `build`, `test` — **not `lint`**. The Netlify deploy pipeline *does* run lint as part of its build gate (`netlify.toml`), meaning lint violations can merge to `main` and only surface at deploy time, not at PR review. `docs/BUILD_022...md`'s own "Verification Commands" section lists `pnpm lint` as expected — the doc and the actual CI config disagree.
- **VERIFIED — a stubbed subsystem exists and is documented as such, not hidden.** `domain_events` (transactional outbox) has a working claim/dispatch/retry/dead-letter worker, but `dispatchEvent()` is a stub — "no webhook target, email provider, or other downstream integration defined anywhere in this codebase yet" (`README.md:115-119`). Trial-expiration reminder emails are similarly "correctly computed and queued" but never sent — no email/SMS provider is wired up anywhere (`20260809162000_billing_usage_enforcement.sql:247-256`). **Practical effect: a trial can silently expire with no warning ever reaching the customer**, because the reminder pipeline stops at a database row.
- **VERIFIED — scalability shortcuts exist and are self-documented.** A migration (`20260729050000_bounded_list_rpcs.sql`) admits several list RPCs "return every non-deleted row for the organization with no limit at all," fixed only with a flat `LIMIT 200/500` and explicitly "no cursor/keyset param is added here." `clients-page.tsx` does a bare `.select("*")` with no `.range()`/`.limit()` at all — true fetch-all. This won't matter at 1 client; it will matter well before an agency reaches hundreds of active clients.
- **VERIFIED — process-events edge function fails open.** If `PROCESS_EVENTS_SECRET` is unset, its shared-secret check is skipped entirely (`process-events/index.ts:63-69`) — low blast radius today only because dispatch is a stub with no PHI in the payload, but this is a fail-open auth pattern that will matter the moment a real integration is wired in.

## Phase 5 — Compliance, security, privacy & multi-tenancy

This is the phase where the gap between "compliant, secure multi-tenant system" as a claim and as a verified fact is largest.

- **VERIFIED — RLS is broadly present** across tenant tables (`clients`, `shifts`, `audit_logs`, `organizations`, `organization_memberships`, `feature_flags`, `files`, `support_access_grants`), gated through a central `has_permission(organization_id, ...)` function.
- **VERIFIED — a severe cross-tenant bypass was live in production until two days before this audit.** `20260809021702_gate_has_permission_bypass_on_active_support_access.sql` documents that `has_permission()` — "the actual gate behind virtually every tenant operational table" — previously returned `true` for **any** platform_owner against **any** organization with no scoping or time limit, making the separately-built support-access-approval system "irrelevant." It also let a platform owner self-approve their own support-access request. This was fixed 2026-08-09; this audit is dated 2026-08-11. **Any claim that the multi-tenant isolation model is proven-secure must be treated as false for any period before that fix, and the fix is too recent to have real-world validation yet.**
- **VERIFIED — a second, still-open cross-tenant PHI leak is explicitly acknowledged in the code, not fixed.** `user_profiles` (home address, languages, skills) is one row per user shared across every organization that user works for. A caregiver's home address entered at Agency A is visible to Agency B if that caregiver also works there. The migration comment states this plainly: "a pre-existing tenant-isolation gap in this schema, not something this build changes" (`20260727050000_caregiver_notes.sql:11-16`). **This is a live, known, unresolved PHI cross-tenant leak as of this audit.**
- **VERIFIED — earlier isolation bugs also existed and were patched** (`20260728040000_isolation_audit_fixes.sql`): staff could read/overwrite another user's profile via a mismatched org/user pair; anyone authenticated could write availability rows into an organization they don't belong to.
- **VERIFIED — audit logging is genuinely tamper-evident.** `audit_logs` has no insert/update/delete policy for any authenticated role; the only writer is a `security definer` trigger. But two production bugs already broke it silently before being caught by live smoke tests (`20260719180000`, `20260719190000`) — audits on `organizations` writes/deletes failed for a period. Not every PHI-adjacent table was confirmed to have an audit trigger (`caregiver_availability`, `incidents`, `caregiver_credentials` — UNKNOWN, not exhaustively checked).
- **VERIFIED — edge functions are mostly well-guarded** (`invite-member`, `update-member-email` both check caller permission before using the service-role client; `submit-document-upload` enforces a 15MB cap and MIME allowlist, itself hardened after a prior bypass). **LIKELY gap:** `process-events` fails open when its shared secret is unset (Phase 4).
- **Pattern, not a single incident:** the migration history shows a recurring cadence — roughly every few weeks — of "audit found a real RLS/permission bug, patched in the same migration," across at least five distinct incidents in the files reviewed. That cadence is evidence of a working audit discipline (bugs get found and fixed), but it is also direct evidence against treating "secure multi-tenant" as a settled, proven claim rather than a continuously-tested one.

**Bottom line for Phase 5:** the architecture and audit discipline are real and above-average for a pre-launch product, but the specific claim "compliant, secure multi-tenant system" should not be repeated to an investor or customer as a settled fact. It is accurate to say "actively audited, with a strong fix cadence and one severe bypass closed two days ago and one known leak still open" — that is a materially different, more defensible claim.

## Phase 6 — Architecture, scalability, vendor dependence & hidden cost

- **VERIFIED — deep Supabase lock-in.** Across 80 migrations: 130 `CREATE FUNCTION`, 57 `CREATE TRIGGER`, 85 `CREATE POLICY` (RLS), 65 indexes. Core business logic — permissioning, invitations, audit writing, billing enforcement — lives in Postgres `security definer` RPCs, not application code. 36 files call `auth.uid()` directly, binding authorization to Supabase Auth's session model. Edge functions use `Deno.serve`, Supabase/Deno-specific. **Migrating off Supabase would be a rewrite, not a swap** — this directly undercuts any narrative that infrastructure is cheaply interchangeable.
- **VERIFIED — the "$25/$599 Supabase" cost story is an infra-tier assumption, not a verified production cost.** No repo evidence of a hardened, differentiated production-PHI environment — one `supabase/config.toml`, one `.env.example`, no separate prod/staging RLS or migration branches. The only HIPAA reference found anywhere is a seeded document-request template string, not infrastructure. **Supabase's BAA (required for real HIPAA coverage) is a paid add-on on top of Team/Enterprise pricing and is not verifiable from this codebase** — whether the $599/mo tier the master plan assumes even includes BAA coverage is UNKNOWN and needs to be confirmed directly with Supabase, not assumed. This is exactly the gap the plan's own caution ("don't confuse the low-cost dev environment with a production-PHI environment") warns about — and the repo shows no evidence that gap has been closed yet, only that it's been correctly flagged.
- **VERIFIED — undisclosed vendor dependence: Stripe and GitHub OAuth.** Stripe subscription state is written directly onto `organizations` and depends on webhook delivery (`STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_STARTER_PRICE_ID` in `.env.example`); GitHub OAuth is the sole sign-in method (`README.md:47-51`, `supabase/config.toml`). Neither is mentioned in the master-plan cost/architecture narrative as summarized. Both are real, hard-to-cheaply-replace dependencies alongside Supabase — Stripe migration means re-plumbing billing-state sync and webhook handling; GitHub-OAuth-only sign-in is also a plausible activation-friction point for non-technical agency owners who don't have (or want) a GitHub account (Phase 3/8 overlap).
- **VERIFIED — scalability shortcuts are self-acknowledged in the code** (see Phase 4): fetch-all queries, flat limits without cursors on several list RPCs.
- **VERIFIED — CI gap:** lint only enforced at Netlify deploy time, not at PR/merge time (Phase 4).
- **VERIFIED — testing/typecheck rigor is genuinely strong**, which is the one place the architecture story is *better* than a skeptical read would assume: near-1:1 test-to-page ratio, `noUncheckedIndexedAccess`/`exactOptionalPropertyTypes` enabled.

## Phase 7 — Pricing, unit economics & business model

- **VERIFIED — Ogevia has a real, live pricing ladder for its own SaaS**, distinct from anything about agency payer billing: Trial (free, 6 weeks, capped at 10 clients/10 caregivers/100 visits), Start $29/mo, Grow $59/mo, Pro $99/mo, Scale $179/mo (annual = ~10x monthly, standard SaaS discount), each with escalating client/caregiver/admin caps, support level, report retention, and bulk-export limits (`20260809161000_billing_plans_and_subscribers.sql:160-212`).
- **VERIFIED — plan changes are properly versioned and audited** (new version row per edit, `is_current` flip, mandatory `change_reason` on every platform-owner mutation, e.g. `upsert_plan_definition()`), and **usage limits are enforced server-side via triggers, not just UI checks** — advisory-locked to prevent race conditions on concurrent seat/client additions (`20260809162000_billing_usage_enforcement.sql:138-179`). This is unusually disciplined for a pre-launch product.
- **VERIFIED — only one plan is actually purchasable today.** `create-checkout-session.ts` hardcodes `STRIPE_STARTER_PRICE_ID` and only ever sells the Start plan; Grow/Pro/Scale exist in the catalog and can be displayed publicly but have no working checkout path yet (comment, `pricing-page.tsx:15-19`, `create-checkout-session.ts:11-14`). **Anyone reading only the pricing page or the schema would overstate current monetizable surface area — three of five tiers are not sellable yet.**
- **CONTRADICTED / naming collision worth flagging explicitly:** the master-plan narrative's "$25/$599 Supabase" and "$0 incremental identifier cost" framing is about Ogevia's *infrastructure cost*. The repo's actual `billing`-named migrations are about *revenue* (what agencies pay Ogevia). These are two different numbers that use the same word ("billing") and are easy to conflate in planning documents — this audit found no repo evidence connecting the two (no cost-per-tenant model, no margin calculation, no infra-cost-vs-plan-price analysis anywhere in code or docs). **Unit economics (infra cost per organization vs. revenue per organization) is UNKNOWN — not computed anywhere in this codebase**, and should not be assumed solved just because both a cost assumption and a pricing ladder separately exist.
- **ASSUMPTION — identifier cost claim is directionally correct but not the real cost driver.** UUID + `client_code` genuinely cost nothing incremental to generate (VERIFIED, Phase 2) — but this was never likely to be the real expense, and the plan's own framing already says as much. The real open cost questions are: BAA-covered tier pricing (UNKNOWN, Phase 6), backup/retention costs for audit-log/PHI data at scale (UNKNOWN — no retention policy found beyond `report_retention_days` on plans, which governs report *access*, not raw data retention), and support cost at "dedicated" tier for Scale customers (UNKNOWN, no cost model in repo).

## Phase 8 — Market, competition, GTM, retention & defensibility

Most of this phase is outside what a codebase can prove. Rather than skip it, each claim is marked honestly.

- **CONFIRMED-AS-UNRESOLVED — the EVV-duplication risk** (developed fully in Phase 2) is the single most important competitive question this audit surfaces: if a target agency already uses a state-mandated EVV system, Ogevia's own clock-in/verify/sign flow is additional caregiver-facing work with zero code-level integration to reduce it. Whether this is fatal, neutral, or actually a selling point ("Ogevia doesn't lock you into a specific EVV vendor") depends entirely on how it's positioned to a buyer — the code cannot answer that, but it can and does confirm the two workflows do not currently talk to each other in any way. **This needs a real answer from actual target-customer conversations, not another planning document.**
- **UNKNOWN — competitive landscape.** No competitor analysis, market sizing, or positioning documents exist in this repo. Nothing here should be read as an assessment of competitors; that work doesn't exist in the codebase to audit.
- **LIKELY overstated in marketing copy, precision-wise — CareScore's "proximity" claim** (Phase 2): marketing describes a "real, computed match score" including proximity; the code shows proximity is a zip/city/state text match, not distance. If a prospect is sold on geolocation-grade matching, the current build under-delivers on that specific word, even though the rest of the score (skills, availability, language, visit history) is real and computed.
- **UNKNOWN — retention mechanics.** No usage/engagement analytics exist in the repo (Phase 3). Retention cannot be assessed from code; only intent (audit trail as a retention lever, compliance tracking as a switching-cost lever) is visible, not outcomes.
- **ASSUMPTION — defensibility via compliance/audit rigor.** The audit-trail tamper-evidence and RBAC model (Phase 5) are genuinely more rigorous than "MVP-grade," which is a plausible moat against less careful competitors *if* the still-open cross-tenant `user_profiles` leak and the recently-closed severe bypass don't undermine that positioning in due diligence. A technical buyer or investor who reads the migration history (as this audit did) will find both the discipline and the incidents; the current codebase supports "we take this seriously and fix things fast," not yet "we have never had a cross-tenant bug."

## Phase 9 — Synthesis, capital allocation & 30-day founder plan

### What this audit actually found, in order of importance

1. **There are two different product pitches in this repository, and they haven't been reconciled.** `PRODUCT_CONSTITUTION.md` says "Workforce Operations Intelligence platform, not an EVV system, not a scheduling app." The master-plan narrative this audit was built from says "reconciliation/billing-readiness layer." The actual shipped surface area (CareScore matching, its own visit verification, credentials, incidents, applicant pipeline, and now full Stripe subscription billing) most closely resembles the first framing, not the second. **This is not a documentation nitpick — it determines what gets built next, who the buyer is being sold to, and what "billing-readiness" is even supposed to mean.** Resolve this before scoping any new build.
2. **A severe cross-tenant RLS bypass was live until two days before this audit, and a second, known cross-tenant PHI leak (`user_profiles`) is still open today.** Whatever gets said publicly or to investors about "secure multi-tenant architecture" needs to be phrased as "actively and successfully audited, with a strong fix cadence" — not as a settled, closed claim. The `user_profiles` leak should be treated as a live compliance risk, not backlog.
3. **The EVV-duplication question is real and unanswered by the code.** Nothing in the repo shows it's been designed away; nothing shows it's been validated as fine. This needs actual target-customer input, not more internal planning.
4. **The infra-cost story ($25/$599 Supabase, $0 identifier cost) is not wrong, but it is not a unit-economics model.** No cost-per-tenant vs. revenue-per-tenant calculation exists anywhere in the repo. BAA-tier pricing for real HIPAA coverage is unverified. Before the next fundraising or pricing conversation, this needs an actual number, not an assumption carried forward from a lower environment tier.
5. **Only one of five priced plans is actually sellable today**, and the platform has one real customer record and zero completed visits as of two days before this audit. Any language implying broad monetized traction would be inaccurate as of this repo state.
6. **The engineering discipline itself is a genuine asset**: strong TypeScript rigor, near-1:1 test coverage, versioned plan/audit data models, server-side enforcement of business rules (not UI-only), and a documented habit of catching and fixing real bugs via structured audits. This is not a "the code is a mess" finding — it's the opposite, and it's worth stating plainly so the real risks (above) aren't read as a general indictment.

### 30-day plan, in priority order

1. **Week 1 — Close the still-open `user_profiles` cross-tenant leak** (Phase 5). This is a live PHI exposure across tenants for any caregiver working at more than one agency; it is the highest-severity unresolved item in this audit and has a known root cause already documented in-repo.
2. **Week 1 — Resolve the product-identity conflict** (Finding 1) at the founder/leadership level, in writing, and update `PRODUCT_CONSTITUTION.md` and whatever external plan documents exist so they agree. Every subsequent roadmap decision depends on this being settled first.
3. **Week 2 — Get a real answer on EVV duplication** from actual prospective agency customers (not internal debate): does their state require a specific EVV vendor, and if so, does Ogevia's own verification step read as redundant, complementary, or replaceable? This should directly shape whether "keep EVV external" stays a design decision or becomes an integration roadmap item.
4. **Week 2 — Turn the cost assumption into a unit-economics model**: confirm actual Supabase production-tier pricing including BAA coverage, estimate audit-log/PHI storage growth per tenant, and compute infra cost against the live plan prices ($29–$179/mo). This is a spreadsheet, not a build — but it doesn't exist yet and should before more plans are marketed as sellable.
5. **Week 3 — Add `pnpm lint` to the GitHub CI gate** (currently only enforced at Netlify deploy time) — small, cheap, closes a real gap between what CI claims to verify and what it verifies.
6. **Week 3 — Decide, explicitly, what happens to a trial that expires with no reminder ever sent.** The reminder pipeline computes and queues correctly but nothing dispatches it — right now a trialing customer can lapse with zero warning, which is a retention problem hiding as a "not yet wired up" scope note.
7. **Week 4 — Finish or explicitly re-scope the CareLik→Ogevia rename** (68 files still reference the old name, including the primary product-constitution document) before any external-facing materials go further — a prospect or investor reading the actual codebase (which this audit just did) will see a majority-CareLik-branded repo under an Ogevia pitch.
8. **Ongoing — treat the fetch-all / unbounded-list pattern as a scheduled, not urgent, fix.** It will not matter at current scale (1 client). It should be on the roadmap before any pilot agency's client count crosses roughly the low hundreds, not built preemptively today.

### What this audit deliberately does not claim

It does not claim the market opportunity is real or fake, that competitors are weaker or stronger, or that the pricing ladder is correctly calibrated — those require information (customer conversations, competitor research, a cost model) that does not exist in this repository, and this audit will not fabricate a market opinion it can't back with evidence. Where Phase 8 says UNKNOWN, that is the honest answer, not a gap in effort.

## Verification Addendum (post-audit, executed testing)

Everything above was static analysis — reading code and migrations, not running anything. At the user's request, a follow-up pass actually executed the codebase in three stages to confirm or correct the findings above. This section records what running code showed, separate from what reading code implied.

### Stage 1 — Local build/test/lint

`pnpm install && pnpm typecheck && pnpm build && pnpm test && pnpm lint` were run directly (not just inspected as CI config).

- **Typecheck:** clean across all 5 packages.
- **Build:** succeeds; `apps/web` produces a single 1.38 MB minified JS bundle (351 KB gzipped) with a Vite chunk-size warning — not previously flagged. Not urgent at current traffic, but worth tracking alongside the other scalability items in Phase 6/9 as the app grows.
- **Test:** **491/491 tests pass** (73 in `@carelik/ui`, 418 in `@carelik/web`) — confirms the "broad test coverage" claim in Phase 4 was not just a file-count ratio, the suite is actually green.

### Stage 2 — Live database verification

Local Supabase (Docker) could not be started in this environment — the sandbox's egress policy returned 403 on every CONNECT to Docker Hub's CDN (`production.cloudfront.docker.com`), a policy denial, not a fixable config issue. Instead, with explicit user confirmation, read-only queries were run directly against the live, connected **`CarelikGlobal`** Supabase project (`cdxxpdyobsqvqveabsda`) via its management API — no writes, no test data, no impersonation.

- **No drift:** the live project's 79 applied migrations match the repo's migration files exactly, including the bypass-fix migration. What was audited statically is what's actually deployed.
- **The severe cross-tenant bypass fix is CONFIRMED deployed and correctly scoped.** Read the live `has_permission()` function source directly: it now requires `is_platform_owner() AND has_active_support_access(target_organization_id)` — the blanket bypass Phase 5 described is genuinely closed in production, not just in a migration file.
- **The `user_profiles`/`feature_flags` bypass is CONFIRMED still live**, at the exact severity described. Read `pg_policies` directly: `users_read_own_profile` and `users_update_own_profile` both still gate on bare `is_platform_owner()`, with no `has_active_support_access()` check — meaning a platform owner can read *and update* any user's profile (home address, languages, skills) without an active, approved support-access grant, right now, in production. This is one degree worse than Phase 5's phrasing ("read/update," confirmed) — worth escalating, not downgrading.
- **RLS confirmed enabled** on all 12 checked PHI/tenant tables (`clients`, `shifts`, `service_visits`, `client_authorizations`, `incidents`, `caregiver_credentials`, `user_profiles`, `audit_logs`, `organizations`, `organization_memberships`, `files`, `caregiver_availability`).
- **`audit_logs` tamper-evidence confirmed live**: exactly one policy exists (`authorized_read_audit`, SELECT-only for `authenticated`) — no insert/update/delete policy for any application role, matching the "only a trigger can write" design.
- **Supabase's own security advisor: zero ERROR-level findings**, 87 WARN + 2 INFO. The overwhelming majority of WARNs (every `SECURITY DEFINER` RPC flagged as "executable by anon/authenticated") are the generic linter's inability to see that this codebase's own architecture doctrine — enforce permissions *inside* each function body, not via grants (`PRODUCT_CONSTITUTION.md`'s "Build for a machine reader too") — makes most of them false positives. Spot-verified on `list_audit_logs`: it's flagged as anon-executable, but its body requires `has_permission(org_id, 'audit.read')`, which resolves false for an unauthenticated caller — no real leak. Two WARNs are genuinely actionable and new to this audit: **leaked-password protection is disabled** in Supabase Auth (a real, low-effort fix), and the `pg_net` extension is installed in the public schema (minor).
- **Performance advisor adds concrete detail to Phase 6's scalability claims**: 47 unindexed foreign keys (mostly `created_by`/`updated_by` audit columns — lower urgency) and, more notably, **10 tables where an RLS policy re-evaluates `auth.uid()` per row** instead of caching it (`(select auth.uid())`) — a known Postgres/Supabase RLS performance anti-pattern that will show up as query latency well before row-count limits do. This is more precise, live evidence for the same concern Phase 6 raised from migration comments alone.

### Stage 3 — Running the app in a browser

The dev server was started locally and pointed at the live `CarelikGlobal` project's public URL and anon key (safe to use client-side by design). Chromium (pre-installed) rendered the marketing, pricing, and login pages at both desktop (1280px) and mobile (390px, iPhone-class) viewports.

- **Confirmed, positive finding not in the original audit:** when the pricing page's data fetch fails, it shows a plain "Could not load plans right now." message — no crash, no blank screen, no unhandled exception. Error-state handling works as designed under a real (if externally-caused) network failure.
- **Correction to an earlier ASSUMPTION:** the login page screenshot shows a full email/password form as the primary sign-in method, with "Sign in with GitHub" offered as a secondary "or" option — not GitHub-only, as `README.md`'s "users sign in with GitHub OAuth" line implies on its own. This **reduces** the activation-friction concern raised in Phase 6/8 (a non-technical agency owner without a GitHub account is not blocked from signing in); the README is simply incomplete on this point, worth a one-line fix.

Testing that flow for real requires either a session without this egress restriction or a device/browser outside this sandbox, logged in with real (or a dedicated test) agency credentials.

### Stage 4 — Attempting to reach the live app directly (user-side test)

With the container-level egress block confirmed, the natural next step was to have the user reach the live app from their own device instead. This surfaced a finding independent of anything above.

- `apps/web/src/lib/tenant-resolver.ts:9-20` states as settled fact that **`app.ogevia.com` is "the real front door now"** for every organization, explaining that wildcard per-tenant subdomains were deliberately dropped for launch because they need a paid Netlify plan.
- **The user navigated to `https://app.ogevia.com/login` from their own device (not this sandbox) and got Netlify's own "Site not found" page** (complete with a Netlify Internal ID), not the app. This is not a DNS failure or a browser error — the request reached Netlify's edge network successfully; Netlify itself reports no site has that hostname configured as a custom domain.
- **This directly contradicts the code's own claim.** Whatever domain configuration `tenant-resolver.ts` assumes is live either was never completed in the Netlify dashboard, was attached to the wrong site, or regressed after being set up. Right now, in production, **the app is not reachable at its documented primary URL for any user** — not just for this audit's sandbox.
- This was independently confirmed (screenshot) rather than inferred, and it's a materially different — and more urgent — kind of gap than anything else in Phases 1-9: those are about whether the *product* is right; this is about whether *anyone can currently reach it at all*. It belongs ahead of, or alongside, item 7 in the Phase 9 30-day plan (finish the CareLik→Ogevia rename), not behind it.
- **Resolved during this session.** The Netlify project (`carelikglobal`) had exactly three production domains configured: `carelikglobal.netlify.app` (default), `www.ogevia.com` (primary, verified via Netlify DNS), and `ogevia.com` (redirects to primary) — `app.ogevia.com` was never added as a domain alias, which is the entire root cause. Since Netlify DNS already manages the `ogevia.com` zone, the user added `app.ogevia.com` as a domain alias directly in the Netlify dashboard; it provisioned (DNS + SSL) within minutes and the user confirmed `https://app.ogevia.com/login` now loads the real login page and successfully authenticated into the live app. **`admin.ogevia.com` (the separate platform-admin host `tenant-resolver.ts`'s `ADMIN_HOSTS` expects) was not confirmed fixed and should be checked the same way** — it was likely never added either, for the same reason.

### Stage 5 — Vendor/customer tenant separation is broken in production (found and partially fixed live)

Once logged into the real app as `admin.carelik@gmail.com` (organization_owner of the `carelik`/Ogevia org), the **Access** page surfaced a finding no amount of code reading would have caught, because it's a data problem, not a code problem.

- **Finding:** `socalcaresservices@gmail.com` — the real paying customer, owner of the `socalcareservices` org ("Socal Care Services llc") — also held `organization_owner` membership **inside `carelik`, the org the rename migration's own comment calls "the platform's own administrative organization, not a tenant workspace."** Confirmed via live query of `organization_memberships`. The user independently identified this as wrong, unprompted, stating the intended model plainly: **"Ogevia is the new SaaS, all other organizations are supposed to be clients."** The live data contradicted that model — the vendor's own internal org and a real client's identity were mixed.
- **Why it matters:** this is exactly the boundary the RLS/multi-tenancy architecture (Phase 5/6) is built to enforce at the data level, blurred at the one place — account/org membership itself — that isn't covered by RLS on operational tables. If anything Ogevia-internal (future admin tooling, other clients' data, plan-management surfaces reachable from an org context) ever lands in the `carelik` org, this customer already had owner-level access to it. It also means the marketing claim "each agency only ever sees its own" (`marketing-page.tsx:30-33`) is true for RLS-covered tables but was not, in practice, true for org membership.
- **Fix applied live, by the user, through the app's own UI** (deliberately not via a direct database write from this session — the app's "Revoke" action runs through proper permission checks and writes a real audit-log entry, which a raw SQL write would bypass): `socalcaresservices@gmail.com`'s `organization_owner` membership in `carelik` was revoked. Re-verified live immediately after: the membership row now shows `status: revoked`; `admin.carelik@gmail.com` remains the sole active owner of `carelik`, and `socalcaresservices@gmail.com`'s access to its own org (`socalcareservices`) and to `ogethinks` is untouched.
- **Not yet resolved — same problem, second instance:** `socalcaresservices@gmail.com` is *also* `organization_owner` of `ogethinks`, a third, separate org. Whether that's the same account legitimately operating a second test/demo client, or the identical vendor/customer boundary problem recurring, is unconfirmed as of this writing — flagged for the user to decide and, if needed, fix the same way.
- **Process recommendation for the 30-day plan:** this class of bug — a real account holding ownership across multiple, supposedly-independent orgs — has no automated check anywhere in the codebase (RLS governs row access within an org, not who gets to *be* a member of which orgs). A periodic manual audit of `organization_memberships` grouped by user, or a one-time cleanup query plus a lightweight admin-side warning ("this email already owns N other organizations"), would have caught this before a live customer ever saw it in their own Access page.

### Net effect of the verification pass

Every specific, checkable claim in the original nine-phase audit held up against actually running the code, the live database, and the live app — nothing was found to be wrong. Two items got worse on inspection (the `user_profiles` leak is a read *and write* hole, not just read), one got better (login isn't GitHub-only), and a few genuinely new items surfaced that static reading couldn't have found (the RLS performance anti-pattern, the disabled leaked-password protection, the bundle-size warning, the confirmed-graceful error state). The one claim that remains untested is also the single most consequential one for the product's core positioning — whether the caregiver's actual on-device verification workflow duplicates state-mandated EVV — and that limitation is now explicit rather than implied.

**Stage 4 changed that ranking, and Stage 5 changed it again.** The app being unreachable at its own documented front door was a precondition for everything else mattering in practice — fixed live during this session by adding `app.ogevia.com` as a Netlify domain alias. That immediately unblocked Stage 5, which found something no static read could: a real paying customer held owner-level access inside Ogevia's own internal org, contradicting the vendor/client separation the whole architecture assumes. Also fixed live, by the user, through the app's own UI. Both fixes are real, confirmed, and already reflected in the live database — but both were found only because testing continued past the point a static audit would have stopped. **The updated priority order coming out of this session: (1) confirm `admin.ogevia.com` has the same missing-domain-alias problem `app.ogevia.com` had, (2) decide and resolve whether `socalcaresservices@gmail.com`'s ownership of `ogethinks` is the same class of bug, (3) then the original item 1, the still-open `user_profiles` read/write leak** — because that leak is now confirmed reachable by real users, where before this session it was only a theoretical one.
